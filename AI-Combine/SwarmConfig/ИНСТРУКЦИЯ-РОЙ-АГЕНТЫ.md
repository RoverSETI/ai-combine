```
   └──────────────────┘  │ ai_ask / ai_agent (роутинг) │
                         └──────────┬──────────────────┘
                                    │ только сложное
                                    ▼
                         ┌─────────────────────┐
                         │ GLM (облако z.ai)   │
                         │ glm_think: думает   │
                         │ glm_review: проверя-│
                         │ ет работу локальных │
                         └─────────────────────┘
```

**Три правила роя (ваши, зафиксированы в swarm.json):**
1. Всё, что можно — **локально**: поиск в интернете, автоматизация ПК, файлы, транскрибация, рутинные тексты.
2. **GLM — только** для самых сложных задач (стратегия, глубокий анализ) и **проверки** того, что наделали локальные агенты. Это «мыслящий контролёр», а не «рабочая рука».
3. **Оркестрация локальная**: маршрутизация по сложности живёт в `~/AiStart/agents.json`, а не в облаке.

### Как задача путешествует по рою (пример)
Вы говорите: «Найди в интернете 3 свежих статьи про btrfs и напиши конспект в заметки».
1. Оркестратор (WebUI-модель) видит: поиск + запись → нужны инструменты.
2. Вызывает `web_search` (локально, DDG) → получает 10 ссылок.
3. Вызывает `web_fetch` на 3 лучших → чистый текст страниц.
4. Сжимает и пишет конспект **локально** (hard-агент).
5. Передаёт черновик в `glm_review`: «верно, нет ошибок, можно дописать про снапшоты».
6. Дописывает и сохраняет заметку через MCP Obsidian.

GLM потратил один вызов на проверку. Всё остальное — ваша видеокарта.

### Как применять (только вручную, только вы!)
```bash
# 1) Посмотреть, что изменится (ничего не трогает):
~/SwarmConfig/apply_swarm.sh diff

# 2) Применить всё (спросит подтверждение):
~/SwarmConfig/apply_swarm.sh apply

# 3) Применить только один блок:
~/SwarmConfig/apply_swarm.sh apply stt     # только транскрибация
~/SwarmConfig/apply_swarm.sh apply tools   # только новые MCP-инструменты

# 4) Откат (бэкапы кладутся в ~/SwarmConfig/backup/):
~/SwarmConfig/apply_swarm.sh rollback
```
Скрипт: делает бэкап → показывает, что именно добавит → ждёт «да» → применяет → перезапускает mcp_server → проверяет инструменты.

## ЧАСТЬ 4. ОБУЧЕНИЕ: как писать агентов

### 4.1 Три уровня «агента» — выбирайте нужный

**Уровень A. Роль в agents.json** (самый простой — это тоже агент).
Роль = модель + параметры + назначение. Когда оркестратор видит задачу, он выбирает роль. Писать нового агента = добавить роль:
```json
"переводчик": {
  "model": "qwen2.5-coder-7b",
  "title": "Переводчик",
  "purpose": "переводы EN↔RU технических текстов",
  "max_tokens": 1500, "temperature": 0.3, "tools": false
}
```
И правило маршрутизации: `{"role": "переводчик", "keywords": ["переведи текст", "translate"]}`.
Правила **не** перекрывающиеся: `hard`-правила проверяются раньше `medium`; первым сработавшим считается то, что выше в списке.

**Уровень B. MCP-инструмент** (когда агенту нужно ДЕЙСТВИЕ).
Инструмент = одна функция с docstring. Правила написания (из практики вашего сервера):
1. Один инструмент — одно действие. «Переведи и сохрани» — это два инструмента.
2. Docstring — на русском, с разделом `Args:` — он попадает в спецификацию для модели.
3. Все аргументы — простые типы (str/int/bool). Модели плохо передают вложенные объекты.
4. Всегда возвращайте строку; ошибки — тоже строкой («⛔ ...»), не исключением: агент должен прочитать причину и скорректироваться.
5. Лимиты везде: таймауты, max_chars, max_steps — иначе агент зациклится или завалит память.
6. Опасное — через deny-лист (уже есть в `run_command`: sudo, rm -rf, mkfs...).

Пример каркаса инструмента (будет сгенерирован apply-скриптом):
```python
@mcp.tool()
def web_search(query: str, limit: int = 5) -> str:
    """Поиск в интернете через DuckDuckGo. Возвращает заголовки, URL, сниппеты.

    Args:
        query: строка поиска
        limit: сколько результатов (1-10)
    """
    # ... реализация, ошибки строкой, таймаут 20с
```

**Уровень C. Многошаговый агент** (уже есть: `ai_agent` / `agent_task`).
Это цикл: модель → вызов инструмента → результат модели → ... → итог.
Когда писать свой: если нужен **специфический протокол** (например, «каждое утро: проскань Habr → сравни с базой → новые статьи в заметки → отчёт»). Иначе используйте готовый `ai_agent` — он универсален.

### 4.2 Как обучить агента (правила и знания)

Знания агента складываются из **четырёх слоёв**:

1. **Системный промпт** (`AGENT_SYSTEM` в mcp_server.py / `system` в роли) — характер, язык, запреты. Коротко: 10-20 строк. Это «характер».
2. **База Знаний WebUI** — факты и документы. Для модели obsidian-knowledge уже подключена. Новые знания: кладите `.md` в vault → `load_knowledge.py` → база обновлена. Это «память-справочник».
3. **Инструменты** — то, агент УМЕЕТ делать, важнее того, что он «знает». Хотите умнее агента — дайте ему инструмент, а не абзац текста.
4. **Примеры (few-shot)** — в purpose роли или в промпте slash-команды: 2-3 пары «вопрос→идеальный ответ» обучают лучше длинной теории.

**Практическое правило:** «Хочу, чтобы агент умел X» → (a) X — это знание? в Знания. (b) X — это действие? MCP-инструмент. (c) X — это стиль/правило? системный промпт роли.

### 4.3 Правила хорошего роя (выстраданные)

- **Один вопрос — один агент.** Не просите fast-агента проанализировать и наоборот.
- **VRAM = 1 модель.** `models-max=1`: смена роли = выгрузка/загрузка (~5-20 сек). Серию задач одной роли делайте подряд.
- **Таймауты честные.** du по всему диску > 60 с — агент потратит все шаги впустую (видели в тесте). В задачах уточняйте: «только /home».
- **GLM не знает ваш компьютер.** В `glm_think` передавайте сжатый контекст: сами соберите факты локально, GLM — только рассуждение.
- **Проверка обязательна для кода.** Любой скрипт, написанный локальным агентом, → `glm_review` перед запуском.

## ЧАСТЬ 5. ОБУЧЕНИЕ: как настраивать меня (ZCode) и WebUI

### 5.1 Память ZCode
У меня есть постоянная память (файлы `memory/*.md`). Она обновляется автоматически по итогам сессий. Ваши правила я фиксирую там же — например, «не писать конфиги в себя» уже записано.

### 5.2 Где что менять (карта настройки)
| Хочу изменить | Файл |
|---|---|
| Роли моделей, маршрутизацию | `~/AiStart/agents.json` |
| Поведение инструментов | `~/AiStart/mcp_server.py` (после apply — `swarm_tools.py`) |
| Правила GLM (когда вызывать) | `~/SwarmConfig/swarm.json → правило_маршрутизации` |
| Транскрибацию | `~/SwarmConfig/stt.json` |
| Slash-команды WebUI | Настройки → Промпты (или API /api/v1/prompts) |
| Базу знаний | vault + `load_knowledge.py` |
| RAG (top_k, гибрид) | Админ → Настройки → Документы |

### 5.3 Порядок внедрения (рекомендую по шагам)
1. `apply_swarm.sh diff` → прочитать, что изменится.
2. `apply_swarm.sh apply tools` → в чате WebUI проверить: «/ai-status» → «найди в интернете курс ЦБ» (web_search).
3. `apply_swarm.sh apply stt` → тест: «транскрибируй файл ~/test.wav».
4. GLM-контур последним: `apply_swarm.sh apply glm` → тест `glm_review` на мелком скрипте.
5. Каждый шаг — я объясняю результат и правлю конфиги по вашим замечаниям.

## ЧАСТЬ 6. БЕЗОПАСНОСТЬ (коротко, но важно)

- GLM-ключ лежит в `~/AiStart/PolzaKey>Z.ai`; инструменты читают его в память процесса и **никогда** не выводят. Не вставляйте ключ в чаты и заметки.
- Все apply-действия — с бэкапом и вашим «да». Откат — одной командой.
- Deny-лист команд действует на всех агентов (sudo, разрушительные rm, mkfs...).
- Микрофон включается только инструментом `stt_listen` при явной задаче.

## ЧАСТЬ 7. Шпаргалка команд

```bash
# Терминал:
~/AiStart/agent_cli.sh status          # роли + VRAM
~/AiStart/agent_cli.sh ask "вопрос"    # авто-выбор агента
~/AiStart/agent_cli.sh agent "задача"  # многошаговый
~/AiStart/agent_cli.sh load hard       # прогреть модель
~/AiStart/agent_cli.sh unload all      # освободить VRAM
~/AiStart/agent_cli.sh route "текст"   # проверить маршрутизацию

# В чате WebUI:
/ai-status                             # статус
/ai поищи курс ЦБ                      # локальный агент (web_search после apply)
/agent проверь диск и доложи           # многошаговый агент
/ai-load hard   /  /ai-unload all      # VRAM

# Применение новых конфигов:
~/SwarmConfig/apply_swarm.sh diff
~/SwarmConfig/apply_swarm.sh apply
```

*Вопросы по любому пункту — спрашивайте, разжую. Следующий логичный шаг: просмотреть `diff` и применить блок `tools`.*
